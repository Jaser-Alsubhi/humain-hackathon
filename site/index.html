Mend

Mend: it diagnoses, fixes and verifies failures on its own, even silent ones.

It reads logs and health checks, finds the cause, takes only allowed actions and checks its own fix. It catches data problems that a healthy-looking site hides, and when no tool can fix the cause it stops and writes an incident ticket instead of guessing.

    How it works

    Observe

    Service status, logs, health and readiness, metrics, database status and config changes. Tool output is wrapped as untrusted text, so a log line cannot give the agent orders.

    Act under a guard

    Only allowlisted actions run. The agent has 12 steps and 4 actions, and the last two steps are reserved for acting and verifying.

    Verify

    Recovered means the site is ready and the data is clean. For silent data problems a healthy page is not enough, so the agent compares the intake journal with the orders and payments tables.

    Escalate

    If the cause is outside what the tools can change, the agent writes a ticket with findings, what it tried and a recommendation, then stops without taking more actions.

    What these results do not show

    • The scenarios were written by the same person who wrote the agent, who knew each fix. They are development scenarios, not a blind test. A held-out set of 12 generated faults is locked, and the agent has not been run on it yet.
    • Runs use temperature 0, so repeats are close to identical. Repeats show stability, not breadth.
    • The hang fix was made after seeing the failures, so the 8 passing hang runs are development results, not a blind test. They also depend on a tool that names the frozen process, and on the 120b model (the 20b model failed one hang run). On the plain frozen backend a blanket restart works just as well and is faster.
    • The live Break it panel runs the same agent on a small shared server. It is limited per visitor and per day, and it only injects the five faults in its list.
    • The unfixable-credentials check looks for keywords. In one run the agent named the access error but blamed the wrong cause.
    • Agent cells pool gpt-oss-120b with a few gpt-oss-20b runs. Early runs used one hosting provider and later runs another, with the same model.
    • The queue-loss scenario is not built.

    Questions

    Why not just a runbook?
    A fixed runbook recovers most outages faster and for free. It does nothing about silent data loss or corruption, it never tells anyone about an unfixable fault, and it fails when connections are exhausted.
    What happens with a fault it cannot fix?
    It escalates with a ticket and takes no repair action. The naive baseline restarts a service on that fault every time.
    How is silent data loss caught?
    The database accepts writes into a table that stores nothing, so every health check passes. The agent compares an append-only journal with the tables, restores the table, then replays the missing rows.
    What did it cost?
    One gpt-oss-120b agent run took about 3,287 to 38,697 tokens and 2 to 213 seconds. The slowest runs were the hangs, mostly waiting on the provider's 5 requests a minute limit.
